# Установщик Nayori

`install.sh` — точка входа в полноэкранный мастер Python/Textual для Arch Linux и
CachyOS. Запускайте из локальной копии репозитория обычным пользователем:

```sh
./install.sh
./install.sh --dry-run
./install.sh --diagnose
```

Нужен терминал от 80×24. На широком экране категории, приложения и описание
расположены в три колонки; на узком — друг под другом. Tab переключает элементы,
стрелки перемещают курсор, Space меняет выбор, Esc возвращает назад, Ctrl+D открывает
диагностику. Категории узкого интерфейса прокручиваются; доступны также мышь и поиск.
При `NO_COLOR=1` сохраняется монохромное отображение.

## Bootstrap и пакеты

Если Python или Textual отсутствуют, скрипт отдельно предлагает
`sudo pacman -S --needed python python-textual`. Отказ завершает запуск.
Системный pip и загрузка исполняемых файлов через curl не используются.
В `--dry-run` и `--diagnose` bootstrap запрещён: при отсутствии Textual выводится
текстовое объяснение. Просмотр плана не создаёт каталогов, журналов или манифестов.

Полное обновление `pacman -Syu` можно выбрать на экране проверки. Отдельного
обновления баз (`pacman -Sy`) нет. Установщик использует локальную базу pacman;
на давно не обновлявшейся системе сначала ознакомьтесь с предлагаемым полным
обновлением. У pacman сохраняются собственные вопросы и подтверждения.

Для AUR используется имеющийся paru, иначе yay. Проверяется существование
выбранных пакетов; без helper AUR пропускается, в плане показывается инструкция
[установки paru](https://github.com/Morganamilo/paru#installation). Сборка идёт
от пользователя, с обычными вопросами helper и возможностью изучить PKGBUILD.
Сам helper установщик не устанавливает. Steam доступен, только если его предоставляет
подключённый репозиторий, например multilib; репозитории не включаются автоматически.

Компоненты описаны в `scripts/installer/catalog.json`: `requires`, `conflicts`,
`incompatible_packages`, `packages`, `package_sources`, `system_requirements`.
Inter устанавливается из репозиториев, Literata — из AUR. Зависимости добавляются
при выборе и повторно проверяются исполнителем. При снятии зависимости снимаются
зависимые пункты. Приложения изначально не выбраны. Пакет уже установлен — повторная
установка не требуется. Недоступный или пропущенный после ошибки пакет блокирует
зависимые компоненты. После ошибки доступны повтор, пропуск и остановка.
Конфликт PulseAudio с выбранной PipeWire-визуализацией также блокирует компонент.

## Версии и пользовательские файлы

При стандартных XDG-путях установка выглядит так:

```text
~/.local/share/nayori/
  releases/<version-id>/        # полная самостоятельная копия оболочки
    manifest.json              # commit, состав, права, типы и SHA-256 файлов
  current -> releases/<version-id>
~/.local/bin/nayori             # стабильная команда запуска и IPC
~/.local/share/applications/nayori.desktop
~/.local/state/nayori/installer/
  installed.json               # активная/предыдущая версия, компоненты, внешние файлы
  transaction.json             # журнал применения / восстановления
  last-install.json            # последняя завершённая установка
  *.log                        # события установки, ошибки и пропуски
```

XDG_DATA_HOME, XDG_CONFIG_HOME и XDG_STATE_HOME учитываются. Управляемые каталоги
и их родители должны принадлежать пользователю или root и не допускать запись
для группы/остальных; симлинки в этих каталогах не принимаются. Сам существующий
`niri` может быть симлинком: сохраняется именно ссылка, её цель не меняется.

Копия сначала создаётся в staging рядом с будущей версией. Проверяются обязательные
ресурсы, соответствие источнику, контрольные суммы, права и ссылки. После публикации
полной версии `current` заменяется одним rename, без промежутка отсутствия указателя.
Каталог старой установки без версионной структуры сохраняется целиком при миграции.
Старые версии и бэкапы автоматически не удаляются.

Перед повторной установкой изменения относительно манифеста выводятся в плане.
Для замены нужна отдельная отметка о сохранении правок в бэкап. Состояние внешних
файлов сохраняется и при последующей установке только приложений. Настройки
`~/.config/nayori/` и данные оболочки установщик не перезаписывает.
Сгенерированные самой оболочкой изменения niri также могут появляться как правки:
установщик консервативно требует подтверждения их замены.

Запуск после установки:

```sh
~/.local/bin/nayori
~/.local/bin/nayori settings
~/.local/bin/nayori ipc launcher toggle
~/.local/bin/nayori status
```

Каталог `~/.local/bin` должен присутствовать в PATH, если нужна короткая команда.
Launcher закрепляет процесс за конкретным каталогом версии и сохраняет PID,
время старта процесса и путь в `$XDG_RUNTIME_DIR/nayori/active.json`. IPC использует
эту работающую версию даже после переключения `current`. Текущий процесс
не перезапускается. Новую версию запускайте после ручного завершения старой.
Процессы, запущенные напрямую через `qs`, не регистрируются в launcher.

## Комплект niri

Источник — `configs/niri/`. Текущий комплект сохраняет раскладки US/RU, управление
окнами и анимации исходной машины. Noctalia, привязки к мониторам, личные приложения
и их автозапуск исключены. Терминал — Kitty, браузер — Firefox, файловый менеджер —
Thunar. Соответствующие пакеты входят в зависимости пресета.

Заменять комплект можно непосредственно в репозитории, сохраняя точки расширения:

- `config.kdl` — основной файл;
- `cfg/keybinds.kdl` — блок `binds` с маркером `// NAYORI_BINDINGS`;
- `cfg/autostart.kdl` — файл, управляемый выбранным автозапуском.

Установщик добавляет бинды только для выбранных функций Nayori и абсолютный путь
к пользовательскому launcher. Временный полный комплект создаётся рядом с niri,
проверяется на недопустимые ссылки и личные пути, затем через `niri validate -c`.
Только успешная проверка разрешает применение. Два переименования каталога
не являются одной атомарной операцией: перед ними сохраняется журнал, исходный
каталог переносится в бэкап, при сбое восстанавливается. Работающий niri может
заметить изменение конфига, поэтому реальную установку следует выполнять в удобное
для изменения рабочего стола время.

Без выбора пресета установщик не редактирует существующий niri. Для выбранного
автозапуска в результате выводится строка `spawn-at-startup` для ручного подключения.

## PAM, SDDM и службы

PAM не импортируется из пользовательского каталога. Используется только
`pam/nayori-lock` из проверяемой копии проекта: обычный файл без симлинков и жёстких
ссылок, допустимый владелец, отсутствие групповой/общей записи. Проверяются также
контролируемые каталоги, идентичность файла при чтении и соответствие копии источнику.
Разрешена только значимая строка `auth required pam_unix.so`, плюс комментарии.
Поскольку оболочка содержит LockService, этот профиль проверяется при каждой
установке самой Nayori, даже если пункт блокировки не выбран. `/etc/pam.d` не меняется.
Это статическая проверка, а не проверка пароля или гарантированного разблокирования.

Тема SDDM и её выбор — отдельные пункты. Выбор пишет
`/etc/sddm.conf.d/90-nayori.conf`; тема размещается в `/usr/share/sddm/themes/nayori`,
данные оформления — в `/var/lib/nayori-sddm`. Используется существующий
`scripts/install-sddm.py` с дополнительным режимом транзакции. Привилегированный
журнал хранится в `/var/lib/nayori-installer/<transaction-id>/` и восстанавливается
через sudo. Пользовательские файлы восстанавливаются после успешного восстановления
этой части. Самостоятельный прежний CLI установки темы также сохранён.

Службы display manager, сети, звука, Bluetooth и питания не переключаются и не
перезапускаются. Недостающие активные службы перечисляются с командами для ручного
включения. При занятом имени уведомлений другой демон не останавливается.

## Восстановление и диагностика

Ctrl+D или `--diagnose` открывают проверку версии, целостности, зависимостей,
niri, PAM, служб, уведомлений, IPC и незавершённых транзакций. Проверка только читает
состояние и не спрашивает пароль. Экспорт JSON выполняется только по отдельному
нажатию, в указанный абсолютный путь; существующий файл не перезаписывается.

На экране доступны действия с отдельным текстовым подтверждением:

- **Восстановить** — отменить прерванную установку;
- **Откат** — вернуть файлы до последней завершённой установки.

Файлы до установки сохраняются рядом: `.NAME.nayori-backup-ID`. Изменения,
обнаруженные при подтверждённом восстановлении, сохраняются в
`.NAME.nayori-displaced-ID`. При конфликте резервной копии восстановление
останавливается с объяснением. Журнал позволяет повторить восстановление после
прерывания. Пакеты остаются установленными; откат не выполняет `pacman -R`.

Журнал `.log` содержит этапы, команды пакетов и результаты. Полный интерактивный
вывод pacman/AUR остаётся в терминале; пароли и ввод подтверждений не записываются.

## Проверки без установки на рабочий стол

```sh
python3 tests/installer.py
```

Нужны Python, Textual и niri для проверки переносимого KDL. Тесты входят в CI unit.
Исполнитель работает во временных XDG-каталогах, pacman/sudo/AUR подменены.
Bootstrap тестируется отдельной копией скрипта в PTY с подменёнными командами.
Launcher проверяется с фиктивным `qs`; Textual — headless через Pilot в 80×24 и
130×40. Службы, текущая сессия, настоящий PAM и пользовательские конфиги не меняются.

## Обновление Nayori

На странице «Обновления» установленная оболочка проверяет последний коммит `main`
репозитория `https://github.com/tatarinovi/Nayori.git` при запуске, каждые шесть
часов и по кнопке. Установка запускается вручную: выбранный коммит проверяется
повторно, копируется в отдельную версию и становится активным. Если `main` успела
измениться, нужно повторить проверку. Предыдущую версию можно вернуть на той же
странице; повторное нажатие переключает версии обратно. Для применения нужно
перезапустить Nayori. Настройки и данные пользователя не заменяются.

Проверка требует Git и сети. При ошибке установленные файлы остаются доступны;
проверку можно повторить вручную. При запуске из рабочего Git-клона проверка и
установка отключены. Ранее установленным копиям сначала потребуется обновление
через установщик из версии, содержащей этот механизм.
